intraday-pnl-explain: reading the code

What the project does, how its seven modules fit together, and which choices affect the meaning of its results.

How to use this

Sections follow the order in which the code runs. Each snippet comes from the file named in its heading. Each number in a Sample data box came from running the pipeline on the tracked files in data/raw/; none was estimated. This page explains structure and behaviour, so it skips routine syntax.

The process in plain English

The project asks whether recent intraday price movement can forecast the next day's movement better than saying "the same as today". It reads minute prices from local files, adds the squared minute-to-minute moves within each day, builds summaries of recent days, and compares three forecasting rules on dates kept out of training. It writes scores, forecasts, fitted weights, and four charts to disk.

01What the project is, and how to run it

The research question from README.md is: can simple lagged intraday realized-variance features forecast next-day realized variance better than naive baselines?

Two terms used throughout:

  • Realized variance — a measure of a price's movement during one trading day, found by adding the squared minute-to-minute returns. A larger value means a choppier day. It is a measurement of the past; it does not forecast the future.
  • Baseline — a simple reference forecast that a model should beat. The main one here is persistence: "tomorrow will be exactly like today".

Everything runs offline from files tracked in the repository. The default path makes no database or network call and needs no credentials.

def load_app_config() -> AppConfig:
    """Load TOML config and resolve script-relative project paths."""
    config_path = Path(__file__).resolve().with_name("config.toml")
    project_root = config_path.parents[3]

    payload = tomllib.loads(config_path.read_text(encoding="utf-8"))
    paths = payload["paths"]
    modeling = payload["modeling"]
    raw_root = project_root / paths["raw_root"]
    default_output_directory = project_root / paths["default_output_directory"]

    return AppConfig(
        project_root=project_root,
        raw_root=raw_root,
        default_output_directory=default_output_directory,
        min_train_dates=int(modeling["min_train_dates"]),
        ridge_alpha=float(modeling["ridge_alpha"]),
    )

03The data contract — load_raw_manifest

def load_raw_manifest(raw_root: Path) -> RawManifest:
    manifest_path = raw_root / "raw_manifest.json"
    payload = json.loads(manifest_path.read_text(encoding="utf-8"))

    # Fail fast when the tracked manifest drifts from the runtime contract.
    missing_keys = REQUIRED_MANIFEST_KEYS.difference(payload)
    if missing_keys:
        missing_keys_text = ", ".join(sorted(missing_keys))
        raise ValueError(f"Raw manifest is missing keys: {missing_keys_text}")

    return RawManifest(
        dataset_name=str(payload["dataset_name"]),
        symbols=list(payload["symbols"]),
        ...
    )
In plain words

Reads the data's description file, checks that all thirteen expected fields are present, and returns a typed object instead of a loose dictionary.

What it does

Input: the folder holding raw_manifest.json. Output: a frozen RawManifest dataclass with thirteen fields. Role: supplies the symbol list and session timezone to the bar loader, and gives the pipeline one clear failure point if the tracked data changes shape.

Why a dataclass rather than the raw dictionary

Field names can be checked by the editor and type checker, which reduces typo-driven runtime errors. The explicit str(), int(), and list() conversions also turn row_count containing the text "23400" into an integer before downstream code uses it.

Trap

The check finds missing keys only. Extra keys are ignored, and values are not validated: nothing here confirms that symbols is a list of strings, that start_date is a valid date, or that row_count matches the files. The test tests/test_raw_contract.py checks the last condition. A corrupted manifest can pass this function and fail later.

04Loading bars — load_raw_intraday_bars

# Regular NYSE cash session window in exchange-local time.
SESSION_START_TIME = time(9, 30)
SESSION_END_TIME = time(15, 59)

def load_raw_intraday_bars(raw_root: Path, manifest: RawManifest) -> pd.DataFrame:
    parquet_paths = discover_raw_parquet_paths(
        raw_root=raw_root, symbols=manifest.symbols
    )
    if not parquet_paths:
        raise ValueError(
            "No tracked raw parquet files were found under data/raw/intraday_bars"
        )

    frames: list[pd.DataFrame] = []
    for parquet_path in parquet_paths:
        frame = pd.read_parquet(parquet_path)
        frames.append(frame)

    bars = pd.concat(frames, ignore_index=True)
    bars = bars.loc[:, manifest.required_columns].copy()

    bars["timestamp"] = pd.to_datetime(bars["timestamp"], utc=True)
    bars = bars.sort_values(["symbol", "timestamp"]).reset_index(drop=True)
    bars = bars.drop_duplicates(subset=["symbol", "timestamp"], keep="last")

    # Keep only bars inside the regular session window in exchange-local time.
    local_timestamps = bars["timestamp"].dt.tz_convert(
        manifest.trading_session_timezone
    )
    local_times = local_timestamps.dt.time
    in_session_mask = (local_times >= SESSION_START_TIME) & (
        local_times <= SESSION_END_TIME
    )
    bars = bars.loc[in_session_mask].reset_index(drop=True)

    return bars
In plain words

Opens one parquet file per symbol, combines them into one table, keeps the four required columns, sorts the rows by time, removes duplicate timestamps, and drops bars outside the regular 09:30–15:59 New York trading window.

What it does

Input: the raw folder and the manifest. Output: one frame with symbol, timestamp (UTC), price, and volume; 23,400 rows for the tracked data. Role: the pipeline's only file-system access for market data.

Why the order of the cleaning steps matters

sort_values runs before drop_duplicates(keep="last"). That makes "last" deterministic after sorting. Deduplicating first would keep whichever row happened to be last in file order, which could change when the files were regenerated.

Trap

Session filtering converts timestamps to local time before comparing them, using manifest.trading_session_timezone. Comparing UTC clock times directly with 09:30 would be wrong because New York is five hours behind UTC in winter and four in summer.

Two sources of truth for the same fact

The window 09:30–15:59 is hard-coded as module constants, while the manifest also stores trading_session = "09:30-15:59". Nothing checks that they match. The timezone is read from the manifest, but the time window is not. A manifest for another exchange would therefore be only partly respected.

Trap in discover_raw_parquet_paths

It searches each symbol's folder and adds the matches to one list. A listed symbol with no folder contributes nothing and raises no error. The ValueError fires only when every symbol is missing, so a run that loses one of six symbols looks healthy.

05The target — construct_daily_realized_variance

# Regular session has 389 one-minute return intervals between 09:30 and 15:59 ET.
EXPECTED_BAR_RETURNS_PER_DAY = 389

def construct_daily_realized_variance(bars: pd.DataFrame) -> pd.DataFrame:
    prepared_bars = bars.copy()
    prepared_bars["timestamp"] = pd.to_datetime(prepared_bars["timestamp"], utc=True)
    prepared_bars = prepared_bars.sort_values(["symbol", "timestamp"]).reset_index(
        drop=True
    )

    # Assign each bar to its New York trading date before aggregating within the day.
    local_date = prepared_bars["timestamp"].dt.tz_convert("America/New_York").dt.date
    prepared_bars["date"] = pd.to_datetime(local_date)

    group_columns = ["symbol", "date"]
    prepared_bars["log_return"] = prepared_bars.groupby(group_columns)[
        "price"
    ].transform(lambda values: np.log(values / values.shift(1)))

    realized_daily = (
        prepared_bars.groupby(group_columns, as_index=False)
        .agg(
            realized_variance=("log_return", _sum_squared_log_returns),
            bar_count=("log_return", _non_missing_log_return_count),
        )
        .sort_values(["symbol", "date"])
        .reset_index(drop=True)
    )

    realized_daily["realized_volatility"] = np.sqrt(realized_daily["realized_variance"])
    realized_daily["is_complete_session"] = (
        realized_daily["bar_count"] >= EXPECTED_BAR_RETURNS_PER_DAY
    )

    return realized_daily
In plain words

For each stock and trading day, it calculates each minute-to-minute price change, squares those changes, and adds them. The result is one measure of daily price movement per stock.

What it does

Input: the 23,400-row bar frame. Output: 60 rows (6 symbols x 10 days) with symbol, date, realized_variance, bar_count, realized_volatility, and is_complete_session. Role: produces the quantity the project forecasts.

The formula

Minute return, for symbol $i$ at minute $t$:

$$r_{i,t} = \log\!\left(\frac{P_{i,t}}{P_{i,t-1}}\right)$$

Daily realized variance and its square root, realized volatility, for trading date $d$:

$$RV_{i,d} = \sum_{t \in d} r_{i,t}^{2}, \qquad RVol_{i,d} = \sqrt{RV_{i,d}}$$

$P_{i,t}$ is symbol $i$'s price at minute $t$, in dollars. $r_{i,t}$ is that minute's log return, a pure number. $\log$ is the natural logarithm. $t \in d$ means all minutes in trading date $d$. $RV_{i,d}$ is in squared decimal-return units; $RVol_{i,d}$ is in decimal return units. The sum has 389 intervals because the first of 390 bars has no earlier bar.

Hand check. The first three minute returns for AAPL on 2026-03-24 are 5.90903638e-05, 5.95624118e-05, and 6.00342148e-05. The sum of the squares of all 389 returns is 1.504149526666387e-06, exactly matching the function. All 60 symbol-days have bar_count = 389, so is_complete_session is True everywhere.

Why returns are computed inside the day, not across it

groupby(["symbol", "date"]) before .shift(1) gives the first bar of each day a missing return, which the sum skips. Shifting across the whole series would compare Monday's 15:59 bar with Tuesday's 09:30 bar. That overnight move could dominate the 389 intraday returns and turn this into a measure of overnight news.

Where 389 comes from

09:30 to 15:59 inclusive contains 390 one-minute timestamps. $15{\times}60 + 59 - (9{\times}60 + 30) = 959 - 570 = 389$ gaps, so 390 bars produce 389 returns. is_complete_session marks a day complete when all 389 are present.

A column nobody reads

is_complete_session is computed here but never used later. The feature stage uses bar_count directly. It is harmless, but it adds a column that suggests a filter the pipeline never applies.

Trap: the timezone is written twice

"America/New_York" is hard-coded here, while the bar loader reads its timezone from manifest.trading_session_timezone. If the manifest named another exchange, the loader would filter that exchange's hours but this function would still assign dates at New York midnight. The mismatch would go unnoticed.

06Features and the leakage rule — build_feature_table

EPSILON_VARIANCE = 1e-12

FEATURE_COLUMNS = [
    "current_log_rv",
    "trailing_5_mean_log_rv",
    "trailing_5_std_log_rv",
    "absolute_1day_log_rv_change",
    "bar_completeness",
]

def build_feature_table(rv_daily: pd.DataFrame) -> pd.DataFrame:
    frame = rv_daily.copy()
    frame["date"] = pd.to_datetime(frame["date"])
    frame = frame.sort_values(["symbol", "date"]).reset_index(drop=True)

    # Log transform stabilizes scale; clip avoids log(0) on quiet days.
    clipped_variance = frame["realized_variance"].clip(lower=EPSILON_VARIANCE)
    frame["log_rv"] = np.log(clipped_variance)

    # The forecast is formed after date d closes, so date-d RV is available.
    # Names say "current" and "trailing" to make that information cutoff explicit.
    frame["current_log_rv"] = frame["log_rv"]
    frame["trailing_5_mean_log_rv"] = frame.groupby("symbol")["log_rv"].transform(
        lambda values: values.rolling(5).mean()
    )
    frame["trailing_5_std_log_rv"] = frame.groupby("symbol")["log_rv"].transform(
        lambda values: values.rolling(5).std()
    )
    frame["absolute_1day_log_rv_change"] = frame.groupby("symbol")["log_rv"].transform(
        lambda values: values.diff().abs()
    )
    frame["bar_completeness"] = frame["bar_count"] / float(EXPECTED_BAR_RETURNS_PER_DAY)

    # Target is next-day log RV; rows without a realized next day are dropped below.
    frame["feature_date"] = frame["date"]
    frame["target_date"] = frame.groupby("symbol")["date"].shift(-1)
    frame["target_log_rv_next_day"] = frame.groupby("symbol")["log_rv"].shift(-1)

    required_columns = FEATURE_COLUMNS + ["target_log_rv_next_day", "target_date"]
    feature_table = frame.dropna(subset=required_columns).copy()
    ...
In plain words

Places the daily movement numbers on a log scale, then builds five summaries of what was known by each stock's closing bell. It also adds the next day's number as the value to predict.

What it does

Input: the 60-row daily realized-variance table. Output: 30 rows with symbol, feature_date, target_date, five feature columns, and target_log_rv_next_day. Role: defines what the models may know and what they must predict.

The formula

Log target, with a floor to keep the logarithm finite on a perfectly flat day:

$$y_{i,d} = \log\!\big(\max(RV_{i,d},\ \varepsilon)\big), \qquad \varepsilon = 10^{-12}$$

The five features for symbol $i$ at feature date $d$:

$$ \begin{aligned} x^{(1)}_{i,d} &= y_{i,d} \\[2pt] x^{(2)}_{i,d} &= \frac{1}{5}\sum_{k=0}^{4} y_{i,d-k} \\[2pt] x^{(3)}_{i,d} &= \sqrt{\frac{1}{4}\sum_{k=0}^{4}\big(y_{i,d-k}-x^{(2)}_{i,d}\big)^{2}} \\[2pt] x^{(4)}_{i,d} &= \big|\,y_{i,d}-y_{i,d-1}\,\big| \\[2pt] x^{(5)}_{i,d} &= \frac{n_{i,d}}{389} \end{aligned} $$

and the label the models must predict:

$$\text{target}_{i,d} = y_{i,d+1}$$

$RV_{i,d}$ is realized variance from section 05. $y_{i,d}$ is its natural logarithm, usually near $-14$ here. $\varepsilon$ is EPSILON_VARIANCE. $x^{(1)}$ is today's level, $x^{(2)}$ the five-day average, $x^{(3)}$ the five-day sample standard deviation (dividing by $5-1=4$, as pandas' rolling(5).std() does by default), $x^{(4)}$ the absolute size of yesterday-to-today's move, and $x^{(5)}$ the share of the 389 expected returns that are present. $d-k$ means the $k$-th earlier row for that symbol, which is the $k$-th earlier trading date, not the calendar date minus $k$ days. $d+1$ likewise means the next trading date for that symbol.

Also, $|-12.316363-(-14.883148)| = 2.566785$, matching absolute_1day_log_rv_change. The target $-16.169420$ is AAPL's log realized variance on the next trading date, 2026-03-31.

Whole sample. The 60 daily rows become 30 feature rows: five feature dates (2026-03-30 through 2026-04-03) for six symbols. The first four dates lack five observations; the last lacks a following day to use as its label.

Why work in logs at all

Realized variance ranges from about $9.5 \times 10^{-8}$ to $4.5 \times 10^{-6}$ here, a factor of about 47, and is always positive. A straight-line model on that scale can be dominated by a busy day and can predict a negative variance. The log scale compresses the range to roughly $-16.2$ to $-12.3$, and exponentiating a prediction always returns a positive variance.

Why the naming is the leakage control

The forecast is made after date $d$ closes, when date $d$'s realized variance is known. That makes current_log_rv valid; it does not need another lag. The word trailing says the rolling windows end at $d$ and do not use later dates. The only unknown is $y_{i,d+1}$, so it is the target and not a feature.

Trap: "next day" is not "tomorrow"

shift(-1) takes the next row for that symbol. From Friday 2026-04-03 to Monday 2026-04-06, that is a three-calendar-day gap; a holiday or missing file could make it longer. The code keeps target_date instead of calculating feature_date + 1 day so the modelling stage can apply the correct information cutoff.

A feature that cannot help

bar_completeness is exactly 1.0 in all 30 rows because every tracked session is complete. A constant column carries no information, so section 07 shows ridge assigning it a weight of exactly zero. It could matter on incomplete data; here it is only a placeholder.

In plain words

Moves one day at a time. At each date it uses only information already known and checked by that evening, fits the model, and forecasts the next day for each stock. Future dates never enter the fit.

What it does

Input: the 30-row feature table, plus min_train_dates and ridge_alpha from the config file. Output: two frames: predictions (one row per model, symbol, and forecast date) and coefficients (the ridge intercept and five weights for each training window). Role: runs the experiment. Earlier stages prepare data; later stages score it.

The three forecasting rules

For symbol $i$ and forecast origin $d$, each rule predicts the next day's log realized variance, $\hat{y}_{i,d+1}$:

$$ \begin{aligned} \text{persistence:} \quad &\hat{y}_{i,d+1} = x^{(1)}_{i,d} = y_{i,d} \\[3pt] \text{rolling mean:} \quad &\hat{y}_{i,d+1} = x^{(2)}_{i,d} = \frac{1}{5}\sum_{k=0}^{4} y_{i,d-k} \\[3pt] \text{ridge:} \quad &\hat{y}_{i,d+1} = b + \sum_{j=1}^{5} \beta_j \tilde{x}^{(j)}_{i,d} \end{aligned} $$

$y_{i,d}$ and $x^{(j)}_{i,d}$ are defined in section 06. $\tilde{x}^{(j)}$ is the standardized version of feature $j$, defined below. $b$ is the fitted intercept and $\beta_j$ is feature $j$'s fitted weight. The two baselines fit nothing; they read one column from the test row.

The formula: standardizing, then ridge

Each feature is centred and rescaled with the mean and standard deviation from the training window only:

$$\tilde{x}^{(j)} = \frac{x^{(j)} - \mu^{(j)}_{\text{train}}}{\sigma^{(j)}_{\text{train}}}, \qquad \sigma^{(j)}_{\text{train}} \leftarrow 1 \ \text{ if } \ \sigma^{(j)}_{\text{train}} = 0$$

Ridge regression then chooses the intercept and weights by minimizing squared error plus a penalty on large weights:

$$\min_{b,\ \beta}\ \sum_{m=1}^{N}\Big(y_m - b - \sum_{j=1}^{5}\beta_j \tilde{x}^{(j)}_m\Big)^{2} \ +\ \alpha \sum_{j=1}^{5} \beta_j^{2}$$

$\mu^{(j)}_{\text{train}}$ and $\sigma^{(j)}_{\text{train}}$ are feature $j$'s mean and standard deviation over the training rows only. The standard deviation is the population version, dividing by $N$, as numpy's .std() does by default. $N$ is the number of training rows; $m$ indexes them; and $y_m$ is that row's true next-day log realized variance. $\alpha$ is ridge_alpha, set to 1.0. The intercept $b$ is not penalized, so standardization puts all five feature weights on the same scale.

The intercept $-14.4428$ is the average training target because standardized features have mean zero. bar_completeness has weight 0.000000: it is 1.0 in every training row, so its standard deviation is zero. _standardize uses 1.0 as the divisor, and $(1.0 - 1.0)/1.0 = 0$ makes the whole column zero.

Why two conditions on the training filter, not one

feature_date < test_date is the usual walk-forward rule. The second condition, target_date <= test_date, handles delayed next observations. If a row dated 2026-04-01 has its next observation on 2026-04-08, using that label for a 2026-04-03 forecast would use information not yet available. The second condition removes it. tests/test_modeling_pipeline.py checks this with a fabricated gap.

Why the scaling moments come from the training window only

_standardize computes the mean and standard deviation from train_values and applies them to both matrices. Computing them from combined data would let the test row affect the fitted scale, a form of look-ahead that can inflate results without using the test label.

Trap: the warm-up is counted twice, and differently

range(min_train_dates, len(unique_dates)) uses min_train_dates as a position in the date list. The len(eligible_train_dates) < min_train_dates check uses it as the count of dates that remain after purging. They differ when a data gap removes rows, so the candidate origin is skipped with continue when too little training data remains.

Trap: min_train_dates has a real cliff

The tracked data has five feature dates. Setting min_train_dates to 5 or more in config.toml means the loop produces no predictions. This used to become KeyError: 'model_name' in the metrics step; the pipeline now raises a clear message. See Fixes applied.

The stated honest weakness

There is one scored date and six forecasts. The six United States (US) large-cap stocks share that day's market move, so they are not six independent observations. Model rankings here are noise. docs/reference/assumptions.md records this limitation.

08Scoring — compute_model_metrics

    for model_name, group in predictions.groupby("model_name"):
        scored_group = group.merge(

        rmse_value = float(np.sqrt(np.square(residual_values).mean()))
        mae_value = float(np.abs(residual_values).mean())
        model_sse = float(np.square(residual_values).sum())
        persistence_sse = float(np.square(persistence_residual_values).sum())

In plain words

For each model, measures how far the forecasts were from the outcomes, then asks whether it beat the reference available at forecast time: "tomorrow equals today".

What it does

Input: the prediction frame. Output: a nested dictionary mapping each model name to {rmse, mae, skill_vs_persistence}, written to metrics.json. Role: produces the project's main comparison.

The formula

Write $e_m = y_m - \hat{y}_m$ for the error on forecast row $m$, over $N$ scored rows. Root mean squared error (RMSE) and mean absolute error (MAE) are:

$$\text{RMSE} = \sqrt{\frac{1}{N}\sum_{m=1}^{N} e_m^{2}}, \qquad \text{MAE} = \frac{1}{N}\sum_{m=1}^{N} \big|e_m\big|$$

Forecast skill compares a model's sum of squared errors (SSE) with persistence's, on exactly the same rows:

$$\text{skill}_M = 1 - \frac{SSE_M}{SSE_P}, \qquad SSE_M = \sum_{m=1}^{N}\big(y_m - \hat{y}^{M}_m\big)^{2}$$

$y_m$ is row $m$'s true next-day log realized variance; $\hat{y}_m$ is its forecast. RMSE means root mean squared error, and MAE means mean absolute error. Both are in log-variance units, so an error of 1.0 means a variance factor of $e \approx 2.72$. $SSE$ means sum of squared errors; $SSE_M$ uses model $M$ and $SSE_P$ uses persistence. Skill is $0$ for persistence, positive when a model beats it, and negative when it does worse. It is bounded above by 1 but has no finite lower bound.

Why persistence is the denominator

An earlier version scored models against the average held-out outcome. That average is not known at forecast time, so it is not a usable benchmark and favours models that predict near the sample mean. Persistence is available on the day, so beating it is a meaningful comparison. The change is recorded in GUIDE_evaluation.md's journal.

Why the merge is so strict

validate="one_to_one" and the row-count check require each model to forecast exactly the same symbol-and-date rows as persistence. Without this, a model could skip its hardest days and report skill on an easier set of rows.

Trap: one branch of the skill guard is missing

The guard returns 0.0 only when both sums of squared errors are zero. If persistence is perfect ($SSE_P = 0$) but the model is not, the expression divides by zero and raises ZeroDivisionError. That exact case is unlikely on real data, but it is not handled.

09Charts — write_diagnostic_figures

In plain words

Writes four Portable Network Graphics (PNG) files: average daily movement over time, ridge forecasts against outcomes, a histogram of errors, and a bar chart of fitted weights.

What it does

Input: the daily realized-variance table, the predictions, the coefficients, and a destination folder. Output: realized_variance_history.png, prediction_vs_actual.png, residual_distribution.png, and coefficient_bar_chart.png. Role: provides a visual check. It returns nothing; the files are the output.

Why every figure goes through _save_figure

It saves each figure and then calls plt.close(figure). Matplotlib keeps open figures in a global registry, so a loop that never closes them leaks memory and eventually warns about too many open figures. Sending all four through one helper makes the close step consistent.

Trap the code used to fall into

Six symbols share each forecast date, so consecutive prediction rows are different stocks, not successive times. A line chart connected unrelated observations into a vertical stripe. The code now plots markers only. See Fixes applied.

Still not a good chart

With one forecast date, Matplotlib's automatic date axis spans roughly four years around that point, leaving the markers in a mostly empty plot. More scored dates would fix this; more plotting code would not. At this sample size, a scatter plot with forecast on one axis and outcome on the other would be more useful.

In plain words

Calls the six stages in order, checks that the experiment produced predictions, then writes the scores, forecasts, weights, and charts to a folder.

What it does

Input: one destination folder. Output: nothing returned; four files and a figures/ subfolder on disk. Role: coordinates the project in twenty lines. Read this file first.

Why no stage keeps state

Each stage is a function that takes tables and returns tables. Nothing is stored between calls, so the notebook can run the same functions in the same order and tests can call one stage with a fabricated table. That lets tests/ check the realized-variance formula with four hand-written bars without using the file system.

What the command-line interface (CLI) adds

cli.py is intentionally small: it builds an argument parser, selects the output directory, calls run_offline_demo, prints the destination, and returns an exit code. --output-dir is resolved with Path(...).resolve(), which is relative to your current shell directory, while the default from the config file is relative to the project root. This keeps an explicitly entered path tied to the directory where it was entered.

Trap: outputs/ is not tracked

.gitignore excludes outputs/ and logs/. Run artifacts are local, so a fresh clone has no outputs/demo_run until the demo runs. Charts already on your machine may therefore be older than the code.

15Limitations, stated honestly

One scored date is not an experiment

Ten trading days lose four to the rolling window and one to the missing next-day label, leaving five feature dates. A four-date warm-up leaves one forecast origin. Every metric rests on six values from one day. The supported conclusion is "the pipeline runs end to end", not "ridge beats persistence".

The data has no known origin

raw_manifest.json records no vendor, extraction date, or method. The reference documents say the prices may be synthetic, so every downstream statistic carries that uncertainty.

No uncertainty on any number

The metrics are point estimates: there is no confidence interval, Diebold-Mariano test (a test of whether one forecast is genuinely better than another), or bootstrap. With six observations, none would be meaningful; the small sample is the deeper problem.

One number per day discards most of the data

The pipeline reads 23,400 minute bars, reduces them to 60 daily numbers, and then to 30 modelling rows. It does not use a jump-robust estimator such as bipower variation, correct for bid-ask bounce, include overnight returns, or check with a signature plot whether one minute is the right sampling interval.

The model set is deliberately small

There are only three rules. There is no heterogeneous autoregressive (HAR) model, which regresses tomorrow's realized variance on daily, weekly, and monthly averages and is a standard benchmark. There is no generalized autoregressive conditional heteroskedasticity (GARCH) model or hyperparameter search. ridge_alpha stays at 1.0 instead of being chosen on a validation window. This is a scope decision stated in the README.

Pooling six symbols into one regression

The ridge model fits one set of weights across all symbols, treating an AAPL row and an XOM row as interchangeable. This assumes the relationship between recent and future movement is the same for every stock, but the assumption is not stated or tested. Residuals within a date are also correlated, which later statistical inference would need to address.
