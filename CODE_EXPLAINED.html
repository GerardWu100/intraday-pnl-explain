intraday-pnl-explain: reading the code

What the project does, how the seven modules fit together, and the handful of decisions that decide whether the numbers mean anything.

How to use this

Sections follow the order the code runs in. Every snippet is copied from the file named in its heading. Every number in a Sample data box came from running the real pipeline on the tracked files in data/raw/ — nothing here is estimated. This page explains structure and behaviour, not syntax; trivial lines are skipped.

The process in plain English

The project asks one question: if you know how choppy a stock's trading was today, can you guess how choppy it will be tomorrow better than by simply saying "the same as today"? It reads minute-by-minute prices from local files, adds up the squared minute-to-minute moves within each day to get a single "how choppy was today" number, builds a few simple summaries of the recent past, then compares three forecasting rules on days the models never saw. It writes the scores, the forecasts, the fitted weights, and four charts to disk.

01What the project is, and how to run it

The research question, taken from README.md: can simple lagged intraday realized-variance features forecast next-day realized variance better than naive baselines?

Two terms, defined before they are used again:

  • Realized variance — a measure of how much a price moved during one trading day, built by adding up the squared minute-to-minute returns. Bigger number, choppier day. It is a measurement of the past, not a forecast.
  • Baseline — a deliberately dumb forecast you must beat before claiming a model works. Here the main one is persistence: "tomorrow will be exactly like today".

Everything runs offline from files tracked in the repository. There is no database call, no network call, and no credential on the default path.

def load_app_config() -> AppConfig:
    """Load TOML config and resolve script-relative project paths."""
    config_path = Path(__file__).resolve().with_name("config.toml")
    project_root = config_path.parents[3]

    payload = tomllib.loads(config_path.read_text(encoding="utf-8"))
    paths = payload["paths"]
    modeling = payload["modeling"]
    raw_root = project_root / paths["raw_root"]
    default_output_directory = project_root / paths["default_output_directory"]

    return AppConfig(
        project_root=project_root,
        raw_root=raw_root,
        default_output_directory=default_output_directory,
        min_train_dates=int(modeling["min_train_dates"]),
        ridge_alpha=float(modeling["ridge_alpha"]),
    )

Why the root is derived, not passed in

Path(__file__).resolve().parents[3] means the pipeline works no matter which directory you launch it from. If it used a relative path like "data/raw" directly, running the code from inside notebooks/ would fail. The notebook still does its own root-finding because it cannot rely on __file__.

Trap

parents[3] is a hard-coded depth. If anyone moves config.py up or down one folder, project_root silently points at the wrong directory and you get a confusing "file not found" rather than a clear error. The depth is a fact about the layout, not a setting, so it cannot live in the config file it is used to find.

03The data contract — load_raw_manifest

def load_raw_manifest(raw_root: Path) -> RawManifest:
    manifest_path = raw_root / "raw_manifest.json"
    payload = json.loads(manifest_path.read_text(encoding="utf-8"))

    # Fail fast when the tracked manifest drifts from the runtime contract.
    missing_keys = REQUIRED_MANIFEST_KEYS.difference(payload)
    if missing_keys:
        missing_keys_text = ", ".join(sorted(missing_keys))
        raise ValueError(f"Raw manifest is missing keys: {missing_keys_text}")

    return RawManifest(
        dataset_name=str(payload["dataset_name"]),
        symbols=list(payload["symbols"]),
        ...
    )
In plain words

Reads the small description file that sits next to the data, checks that all thirteen expected fields are there, and hands back a typed object instead of a loose dictionary.

What it does

Input: the folder holding raw_manifest.json. Output: a frozen RawManifest dataclass with thirteen fields. Role: supplies the symbol list and the session timezone to the bar loader, and gives the whole pipeline one loud failure point if the tracked data changes shape.

Why a dataclass rather than the raw dictionary

Two reasons. Field names get checked by the editor and the type checker instead of by a typo at run time. And the explicit str(), int(), list() casts mean a manifest that stores row_count as the text "23400" still produces an integer downstream, rather than failing much later inside a comparison.

Trap

The check is missing keys only. Extra keys are accepted and ignored, and no value is validated: nothing confirms that symbols is a list of strings, that start_date parses as a date, or that row_count matches the files. The last of those is checked, but by a test (tests/test_raw_contract.py), not by the loader. A corrupted manifest passes this function and fails later.

04Loading bars — load_raw_intraday_bars

# Regular NYSE cash session window in exchange-local time.
SESSION_START_TIME = time(9, 30)
SESSION_END_TIME = time(15, 59)

def load_raw_intraday_bars(raw_root: Path, manifest: RawManifest) -> pd.DataFrame:
    parquet_paths = discover_raw_parquet_paths(
        raw_root=raw_root, symbols=manifest.symbols
    )
    if not parquet_paths:
        raise ValueError(
            "No tracked raw parquet files were found under data/raw/intraday_bars"
        )

    frames: list[pd.DataFrame] = []
    for parquet_path in parquet_paths:
        frame = pd.read_parquet(parquet_path)
        frames.append(frame)

    bars = pd.concat(frames, ignore_index=True)
    bars = bars.loc[:, manifest.required_columns].copy()

    bars["timestamp"] = pd.to_datetime(bars["timestamp"], utc=True)
    bars = bars.sort_values(["symbol", "timestamp"]).reset_index(drop=True)
    bars = bars.drop_duplicates(subset=["symbol", "timestamp"], keep="last")

    # Keep only bars inside the regular session window in exchange-local time.
    local_timestamps = bars["timestamp"].dt.tz_convert(
        manifest.trading_session_timezone
    )
    local_times = local_timestamps.dt.time
    in_session_mask = (local_times >= SESSION_START_TIME) & (
        local_times <= SESSION_END_TIME
    )
    bars = bars.loc[in_session_mask].reset_index(drop=True)

    return bars
In plain words

Opens one parquet file per symbol, stacks them into a single table, keeps only the four agreed columns, puts the rows in time order, throws away duplicate timestamps, and drops any bar outside the regular 09:30–15:59 New York trading window.

What it does

Input: the raw folder and the manifest. Output: a single frame with columns symbol, timestamp (UTC), price, volume — 23,400 rows on the tracked data. Role: the only place the pipeline touches the file system for market data.

Why the order of the cleaning steps matters

sort_values runs before drop_duplicates(keep="last"). Sorting first makes "last" mean "the last row for that timestamp after ordering", which is deterministic. Deduplicating first would leave whichever row happened to arrive last in file order — a result that could change if the files were regenerated.

Trap

Session filtering converts to local time before comparing, using manifest.trading_session_timezone. Comparing raw UTC clock times against 09:30 would be wrong twice a year, because New York is five hours behind UTC in winter and four in summer, so the session sits at a different UTC time in each half of the year.

Two sources of truth for the same fact

The window 09:30–15:59 is hard-coded as module constants, while the manifest separately carries trading_session = "09:30-15:59". Nothing checks that the two agree. The timezone is read from the manifest, so the code half-trusts the manifest and half-ignores it. Today the two match, so behaviour is correct; a manifest describing a different exchange would be silently half-honoured.

Trap in discover_raw_parquet_paths

It globs each symbol's folder and extends the list. A symbol listed in the manifest with no folder on disk contributes nothing and raises nothing. The ValueError only fires if every symbol is missing. A run that quietly loses one of six symbols looks identical to a healthy run.

05The target — construct_daily_realized_variance

# Regular session has 389 one-minute return intervals between 09:30 and 15:59 ET.
EXPECTED_BAR_RETURNS_PER_DAY = 389

def construct_daily_realized_variance(bars: pd.DataFrame) -> pd.DataFrame:
    prepared_bars = bars.copy()
    prepared_bars["timestamp"] = pd.to_datetime(prepared_bars["timestamp"], utc=True)
    prepared_bars = prepared_bars.sort_values(["symbol", "timestamp"]).reset_index(
        drop=True
    )

    # Assign each bar to its New York trading date before aggregating within the day.
    local_date = prepared_bars["timestamp"].dt.tz_convert("America/New_York").dt.date
    prepared_bars["date"] = pd.to_datetime(local_date)

    group_columns = ["symbol", "date"]
    prepared_bars["log_return"] = prepared_bars.groupby(group_columns)[
        "price"
    ].transform(lambda values: np.log(values / values.shift(1)))

    realized_daily = (
        prepared_bars.groupby(group_columns, as_index=False)
        .agg(
            realized_variance=("log_return", _sum_squared_log_returns),
            bar_count=("log_return", _non_missing_log_return_count),
        )
        .sort_values(["symbol", "date"])
        .reset_index(drop=True)
    )

    realized_daily["realized_volatility"] = np.sqrt(realized_daily["realized_variance"])
    realized_daily["is_complete_session"] = (
        realized_daily["bar_count"] >= EXPECTED_BAR_RETURNS_PER_DAY
    )

    return realized_daily
In plain words

For each stock and each trading day, it works out how much the price changed from one minute to the next, squares each of those changes, and adds them all up. One number per stock per day saying how choppy that day was.

What it does

Input: the 23,400-row bar frame. Output: 60 rows (6 symbols x 10 days) with symbol, date, realized_variance, bar_count, realized_volatility, is_complete_session. Role: this is the quantity the whole project forecasts.

The formula

Minute return, for symbol $i$ at minute $t$:

$$r_{i,t} = \log\!\left(\frac{P_{i,t}}{P_{i,t-1}}\right)$$

Daily realized variance and its square root, realized volatility, for trading date $d$:

$$RV_{i,d} = \sum_{t \in d} r_{i,t}^{2}, \qquad RVol_{i,d} = \sqrt{RV_{i,d}}$$

$P_{i,t}$ is the price of symbol $i$ recorded at minute $t$, in dollars. $r_{i,t}$ is the log return over that minute, a pure number. $\log$ is the natural logarithm. $t \in d$ means "all minutes belonging to trading date $d$". $RV_{i,d}$ has units of decimal-return squared; $RVol_{i,d}$ has units of decimal return. The sum runs over the 389 minute intervals inside a full 390-bar session, because the first bar of the day has no preceding bar to compare against.

Hand check. The first three minute returns for AAPL on 2026-03-24 are 5.90903638e-05, 5.95624118e-05 and 6.00342148e-05. Summing the squares of all 389 of them by hand gives 1.504149526666387e-06, which is exactly what the function returns. Across the whole sample all 60 symbol-days have bar_count = 389, so is_complete_session is True everywhere.

Why returns are computed inside the day, not across it

groupby(["symbol", "date"]) before .shift(1) means the first bar of each day has no previous bar and yields a missing value, which the sum skips. Shifting across the whole series instead would create one "return" spanning from 15:59 on Monday to 09:30 on Tuesday. That overnight gap is usually the single largest move of the day and would swamp the 389 real minute returns, turning a measure of intraday choppiness into a measure of overnight news.

Where 389 comes from

09:30 to 15:59 inclusive, at one-minute spacing, is 390 timestamps. $15{\times}60 + 59 - (9{\times}60 + 30) = 959 - 570 = 389$ gaps between them, so 390 bars produce 389 returns. is_complete_session flags a day as complete when it has all 389.

A column nobody reads

is_complete_session is computed here and never used again anywhere in the pipeline. The feature stage uses bar_count directly instead. It is not wrong, it is just dead weight, and a reader may waste time looking for the filter it implies.

Trap: the timezone is written twice

"America/New_York" is hard-coded here, but the bar loader took the same timezone from manifest.trading_session_timezone. If a manifest ever named a different exchange, the loader would filter in that exchange's hours while this function would still cut days at New York midnight. The two would disagree and nothing would complain.

06Features and the leakage rule — build_feature_table

EPSILON_VARIANCE = 1e-12

FEATURE_COLUMNS = [
    "current_log_rv",
    "trailing_5_mean_log_rv",
    "trailing_5_std_log_rv",
    "absolute_1day_log_rv_change",
    "bar_completeness",
]

def build_feature_table(rv_daily: pd.DataFrame) -> pd.DataFrame:
    frame = rv_daily.copy()
    frame["date"] = pd.to_datetime(frame["date"])
    frame = frame.sort_values(["symbol", "date"]).reset_index(drop=True)

    # Log transform stabilizes scale; clip avoids log(0) on quiet days.
    clipped_variance = frame["realized_variance"].clip(lower=EPSILON_VARIANCE)
    frame["log_rv"] = np.log(clipped_variance)

    # The forecast is formed after date d closes, so date-d RV is available.
    # Names say "current" and "trailing" to make that information cutoff explicit.
    frame["current_log_rv"] = frame["log_rv"]
    frame["trailing_5_mean_log_rv"] = frame.groupby("symbol")["log_rv"].transform(
        lambda values: values.rolling(5).mean()
    )
    frame["trailing_5_std_log_rv"] = frame.groupby("symbol")["log_rv"].transform(
        lambda values: values.rolling(5).std()
    )
    frame["absolute_1day_log_rv_change"] = frame.groupby("symbol")["log_rv"].transform(
        lambda values: values.diff().abs()
    )
    frame["bar_completeness"] = frame["bar_count"] / float(EXPECTED_BAR_RETURNS_PER_DAY)

    # Target is next-day log RV; rows without a realized next day are dropped below.
    frame["feature_date"] = frame["date"]
    frame["target_date"] = frame.groupby("symbol")["date"].shift(-1)
    frame["target_log_rv_next_day"] = frame.groupby("symbol")["log_rv"].shift(-1)

    required_columns = FEATURE_COLUMNS + ["target_log_rv_next_day", "target_date"]
    feature_table = frame.dropna(subset=required_columns).copy()
    ...
In plain words

Takes the daily choppiness numbers, puts them on a log scale, and for each stock and each day builds five summaries of what was known by the closing bell — plus the answer it is trying to predict, which is the next day's number.

What it does

Input: the 60-row daily realized-variance table. Output: 30 rows with symbol, feature_date, target_date, the five feature columns, and target_log_rv_next_day. Role: defines exactly what the models are allowed to know and what they must guess.

The formula

Log target, with a floor to keep the logarithm finite on a perfectly flat day:

$$y_{i,d} = \log\!\big(\max(RV_{i,d},\ \varepsilon)\big), \qquad \varepsilon = 10^{-12}$$

The five features for symbol $i$ at feature date $d$:

$$ \begin{aligned} x^{(1)}_{i,d} &= y_{i,d} \\[2pt] x^{(2)}_{i,d} &= \frac{1}{5}\sum_{k=0}^{4} y_{i,d-k} \\[2pt] x^{(3)}_{i,d} &= \sqrt{\frac{1}{4}\sum_{k=0}^{4}\big(y_{i,d-k}-x^{(2)}_{i,d}\big)^{2}} \\[2pt] x^{(4)}_{i,d} &= \big|\,y_{i,d}-y_{i,d-1}\,\big| \\[2pt] x^{(5)}_{i,d} &= \frac{n_{i,d}}{389} \end{aligned} $$

and the label the models must predict:

$$\text{target}_{i,d} = y_{i,d+1}$$

$RV_{i,d}$ is the realized variance from section 05. $y_{i,d}$ is its natural logarithm, a pure number, typically near $-14$ on this data. $\varepsilon$ is the floor EPSILON_VARIANCE. $x^{(1)}$ is today's level, $x^{(2)}$ the five-day average, $x^{(3)}$ the five-day sample standard deviation (dividing by $5-1=4$, which is what pandas' rolling(5).std() does by default), $x^{(4)}$ the size of yesterday-to-today's move regardless of direction, and $x^{(5)}$ the share of the 389 expected minute returns actually present. $d-k$ means the $k$-th earlier row for that symbol, which is the $k$-th earlier trading date, not the calendar date minus $k$ days. $d+1$ likewise means the next trading date for that symbol.

Hand check. The mean of the five values on the left is $(-13.407283-13.793275-12.704303-14.883148-12.316363)/5 = -13.420874$, which matches trailing_5_mean_log_rv exactly. And $|-12.316363-(-14.883148)| = 2.566785$ matches absolute_1day_log_rv_change. The target $-16.169420$ is AAPL's log realized variance on 2026-03-31, the next trading date.

Whole sample. 60 daily rows become 30 feature rows: five feature dates (2026-03-30 through 2026-04-03) times six symbols. The first four dates are lost to the five-day rolling window and the last date is lost because it has no following day to label it.

Why work in logs at all

Realized variance on this data ranges from about $9.5 \times 10^{-8}$ to $4.5 \times 10^{-6}$ — a factor of about 47 between the quiet days and the choppy ones, and always positive. Fitting a straight line to numbers like that lets one busy day dominate the whole fit, and the fitted line can predict a negative variance, which is impossible. On the log scale the same range becomes roughly $-16.2$ to $-12.3$, well behaved for a linear model, and exponentiating any prediction gives back a positive variance.

Why the naming is the leakage control

The forecast is made after date $d$'s closing bell. At that moment date $d$'s realized variance is already measured, so using it is not cheating — hence current_log_rv rather than a lag. The word trailing in the rolling columns says the window ends at $d$ and never reaches past it. The one thing not known at that moment is $y_{i,d+1}$, which is why it is the target and appears in no feature.

Trap: "next day" is not "tomorrow"

shift(-1) takes the next row for that symbol. Over the Friday 2026-04-03 to Monday 2026-04-06 weekend it produces a three-calendar-day gap, and after a holiday or a missing file it could be longer still. That is why target_date is carried as its own column instead of being reconstructed as feature_date + 1 day: the modelling stage needs the real date to decide what was knowable when.

A feature that cannot help

bar_completeness equals exactly 1.0 in all 30 rows, because every session in the tracked payload is complete. A column with no variation carries no information; section 07 shows the ridge model duly gives it a weight of exactly zero. It would matter on messier data, but on this data it is a placeholder.

07Walk-forward training — build_walk_forward_predictions

BASELINE_FEATURE_COLUMNS: dict[str, str] = {
    "persistence": "current_log_rv",
    "rolling_mean": "trailing_5_mean_log_rv",
}

    # Expand one forecast-origin date at a time. A training label is eligible only
    # when its target has been observed by the test date's post-close cutoff.
    for date_index in range(min_train_dates, len(unique_dates)):
        test_date = unique_dates[date_index]
        train_frame = frame[
            (frame["feature_date"] < test_date) & (frame["target_date"] <= test_date)
        ].copy()
        test_frame = frame[frame["feature_date"] == test_date].copy()
        eligible_train_dates = sorted(train_frame["feature_date"].unique())
        if len(eligible_train_dates) < min_train_dates or test_frame.empty:
            continue

        for model_name, feature_column in BASELINE_FEATURE_COLUMNS.items():
            baseline_predictions = test_frame[feature_column].to_numpy(dtype=float)
            _append_prediction_rows(...)

        train_x = train_frame.loc[:, FEATURE_COLUMNS].to_numpy(dtype=float)
        train_y = train_frame["target_log_rv_next_day"].to_numpy(dtype=float)
        test_x = test_frame.loc[:, FEATURE_COLUMNS].to_numpy(dtype=float)

        train_x_scaled, test_x_scaled = _standardize(
            train_values=train_x, test_values=test_x
        )

        ridge_model = Ridge(alpha=ridge_alpha)
        ridge_model.fit(train_x_scaled, train_y)
        ridge_predictions = ridge_model.predict(test_x_scaled)
In plain words

Steps forward one day at a time. On each step it takes everything that was already known and already checkable on that evening, fits the model to it, and makes one forecast per stock for the next day. It never looks at a day it has not reached yet.

What it does

Input: the 30-row feature table, plus min_train_dates and ridge_alpha from the config file. Output: two frames — predictions (one row per model, symbol and forecast date) and coefficients (the ridge intercept and five weights per training window). Role: the actual experiment. Everything before it prepares data; everything after it scores.

The three forecasting rules

For symbol $i$ and forecast origin $d$, each rule produces a guess $\hat{y}_{i,d+1}$ of the next day's log realized variance:

$$ \begin{aligned} \text{persistence:} \quad &\hat{y}_{i,d+1} = x^{(1)}_{i,d} = y_{i,d} \\[3pt] \text{rolling mean:} \quad &\hat{y}_{i,d+1} = x^{(2)}_{i,d} = \frac{1}{5}\sum_{k=0}^{4} y_{i,d-k} \\[3pt] \text{ridge:} \quad &\hat{y}_{i,d+1} = b + \sum_{j=1}^{5} \beta_j \tilde{x}^{(j)}_{i,d} \end{aligned} $$

$y_{i,d}$ and $x^{(j)}_{i,d}$ are exactly the quantities defined in section 06. $\tilde{x}^{(j)}$ is the standardized version of feature $j$, defined just below. $b$ is the fitted intercept and $\beta_j$ the fitted weight on feature $j$. The two baselines fit nothing: they simply read one column straight off the test row.

The formula: standardizing, then ridge

Each feature is centred and rescaled using only the training window's mean and standard deviation:

$$\tilde{x}^{(j)} = \frac{x^{(j)} - \mu^{(j)}_{\text{train}}}{\sigma^{(j)}_{\text{train}}}, \qquad \sigma^{(j)}_{\text{train}} \leftarrow 1 \ \text{ if } \ \sigma^{(j)}_{\text{train}} = 0$$

Ridge regression then picks the intercept and weights that minimise squared error plus a penalty on the size of the weights:

$$\min_{b,\ \beta}\ \sum_{m=1}^{N}\Big(y_m - b - \sum_{j=1}^{5}\beta_j \tilde{x}^{(j)}_m\Big)^{2} \ +\ \alpha \sum_{j=1}^{5} \beta_j^{2}$$

$\mu^{(j)}_{\text{train}}$ and $\sigma^{(j)}_{\text{train}}$ are the mean and standard deviation of feature $j$ over the training rows only (population standard deviation, dividing by $N$, which is what numpy's .std() does by default). $N$ is the number of training rows, $m$ indexes them, $y_m$ is that row's true next-day log realized variance. $\alpha$ is ridge_alpha from the config file, set to 1.0. The intercept $b$ is not penalised, which is why standardizing matters: the penalty treats all five weights on the same footing only if the features share a scale.

3 models x 6 symbols x 1 scored date = 18 prediction rows. The intercept $-14.4428$ is the average training target, because standardized features have mean zero. bar_completeness gets a weight of exactly 0.000000: it is 1.0 in every training row, so its standard deviation is zero, _standardize replaces the divisor with 1.0, and $(1.0 - 1.0)/1.0 = 0$ makes the whole column zeros, which ridge cannot use.

Why two conditions on the training filter, not one

feature_date < test_date alone would be the usual walk-forward rule. The second condition, target_date <= test_date, handles the case where a symbol's next observation is far away. Imagine a row with feature date 2026-04-01 whose next observation for that symbol is 2026-04-08 because of a data gap. Its label is a fact about 2026-04-08. Training on it while forecasting from 2026-04-03 would feed the model an outcome nobody could have known — classic look-ahead. The second condition drops it. tests/test_modeling_pipeline.py checks precisely this with a fabricated gap.

Why the scaling moments come from the training window only

_standardize computes the mean and standard deviation from train_values and applies them to both matrices. Computing them over the combined data would let the test row's own level leak into the numbers used to fit — a subtle form of look-ahead that inflates results without ever touching the label.

Trap: the warm-up is counted twice, and differently

range(min_train_dates, len(unique_dates)) uses min_train_dates as a position in the date list. The check len(eligible_train_dates) < min_train_dates then uses it as a count of dates that survived purging. The two agree only when no rows are purged. When a gap removes a date, the loop reaches a candidate origin whose eligible training set is too small and skips it with continue, which is the correct behaviour but reads as a redundant check until you work through the gap case.

Trap: min_train_dates has a real cliff

The tracked data has five feature dates. Set min_train_dates to 5 or more in config.toml and the loop body never executes, producing zero predictions. That used to surface as a confusing KeyError: 'model_name' inside the metrics step; the pipeline now raises a clear message instead. See Fixes applied.

The stated honest weakness

One scored date. Six forecasts. The six are all US large-cap stocks on the same day, so they share the same market move and are nowhere near six independent observations. Any ranking of the three models here is noise. docs/reference/assumptions.md says this in as many words, and it is the right call to say it rather than dress the numbers up.

08Scoring — compute_model_metrics

    for model_name, group in predictions.groupby("model_name"):
        scored_group = group.merge(
            persistence_rows,
            on=observation_columns,
            how="inner",
            validate="one_to_one",
        )
        if len(scored_group.index) != len(group.index):
            raise ValueError(
                f"Model {model_name!r} does not share every row with persistence"
            )

        residual_values = actual_values - predicted_values
        persistence_residual_values = actual_values - persistence_values

        rmse_value = float(np.sqrt(np.square(residual_values).mean()))
        mae_value = float(np.abs(residual_values).mean())
        model_sse = float(np.square(residual_values).sum())
        persistence_sse = float(np.square(persistence_residual_values).sum())
        skill_value = (
            0.0
            if persistence_sse == 0.0 and model_sse == 0.0
            else float(1.0 - model_sse / persistence_sse)
        )
In plain words

For each model it measures how far the forecasts were from the truth, then asks the only question that matters: was it better or worse than simply saying "tomorrow equals today"?

What it does

Input: the prediction frame. Output: a nested dictionary, model name to {rmse, mae, skill_vs_persistence}, written straight to metrics.json. Role: the project's headline answer.

The formula

Write $e_m = y_m - \hat{y}_m$ for the error on forecast row $m$, over $N$ scored rows:

$$\text{RMSE} = \sqrt{\frac{1}{N}\sum_{m=1}^{N} e_m^{2}}, \qquad \text{MAE} = \frac{1}{N}\sum_{m=1}^{N} \big|e_m\big|$$

Forecast skill compares a model's total squared error against persistence's, on exactly the same rows:

$$\text{skill}_M = 1 - \frac{SSE_M}{SSE_P}, \qquad SSE_M = \sum_{m=1}^{N}\big(y_m - \hat{y}^{M}_m\big)^{2}$$

$y_m$ is the true next-day log realized variance for row $m$; $\hat{y}_m$ is the forecast. RMSE stands for root mean squared error and MAE for mean absolute error; both are in log-variance units, so a value of 1.0 means the forecast was off by a factor of $e \approx 2.72$ in variance terms. $SSE$ stands for sum of squared errors. $SSE_M$ uses model $M$'s forecasts and $SSE_P$ persistence's. Skill is $0$ for persistence itself by construction, positive when a model beats persistence, and negative when it is worse. It has no upper bound below 1 and no lower bound above minus infinity.

Hand check. Ridge skill $= 1 - 8.497269/10.138489 = 0.161880$, matching the file. Persistence RMSE $= \sqrt{10.138489/6} = 1.299903$, also matching. These six numbers come from a single forecast date; see the limitations section before reading anything into them.

Why persistence is the denominator

An earlier version of this code scored models against the average of the held-out outcomes. That average is not knowable at forecast time, so it is not a benchmark anyone could have traded against — it flatters any model that merely predicts near the sample mean. Persistence is something a person could actually have done on the day, so beating it is a real claim. The change is recorded in GUIDE_evaluation.md's journal.

Why the merge is so strict

validate="one_to_one" plus the row-count equality check means a model is scored only if it forecast exactly the same symbol-and-date rows as persistence, no more and no fewer. Without it, a model that quietly skipped its hardest days would show a flattering skill number computed against a different, easier denominator.

Trap: one branch of the skill guard is missing

The guard returns 0.0 only when both sums of squared errors are zero. If persistence is perfect ($SSE_P = 0$) while the model is not, the expression divides a positive float by 0.0 and raises ZeroDivisionError. It needs a forecast that is right to the last floating-point bit, so it will not happen on real data, but it is a genuine hole rather than a handled case.

09Charts — write_diagnostic_figures

In plain words

Writes four PNG files: the average daily choppiness over time, ridge forecasts against what actually happened, a histogram of the misses, and a bar chart of the fitted weights.

What it does

Input: the daily realized-variance table, the predictions, the coefficients, and a destination folder. Output: realized_variance_history.png, prediction_vs_actual.png, residual_distribution.png, coefficient_bar_chart.png. Role: the eyeball check. It returns nothing; the files are the product.

Why every figure goes through _save_figure

It saves and then calls plt.close(figure). Matplotlib keeps every figure alive in a global registry until it is closed, so a loop that builds figures without closing them leaks memory and eventually prints a warning about too many open figures. Routing all four through one helper makes forgetting impossible.

Trap the code used to fall into

Six symbols share the same forecast date, so consecutive rows of the prediction frame are different stocks, not successive points in time. Drawing them with a line chart invented a path between unrelated observations and rendered as a single vertical stripe. It now plots markers only. See Fixes applied.

Still not a good chart

With one forecast date, matplotlib's automatic date axis pads out to roughly a four-year span around that single point, so the markers huddle in the middle of an almost empty plot. The fix is more scored dates, not more plotting code. A predicted-against-actual scatter, with forecast on one axis and outcome on the other, would be the more informative chart at this sample size.

In plain words

Calls the six stages in order, checks that the experiment actually produced something, then writes the scores, the forecasts, the weights and the charts to a folder.

What it does

Input: one destination folder. Output: nothing returned; four files plus a figures/ subfolder on disk. Role: the whole project in twenty lines. This is the file to read first.

Why no stage keeps state

Every stage is a plain function taking frames and returning frames. Nothing is stored on an object between calls, so the notebook can call exactly the same functions in exactly the same order and get the same answer, and a test can call any single stage with a fabricated frame. That is why tests/ can check the realized-variance formula against four hand-written bars without touching the file system.

What the CLI adds

cli.py is thin on purpose: build an argument parser, pick the output directory, call run_offline_demo, print where the files went, return an exit code. --output-dir is resolved with Path(...).resolve(), which is relative to your current shell directory, while the default from the config file is relative to the project root. The two behave differently on purpose: a path you typed should mean what you meant.

Trap: outputs/ is not tracked

.gitignore excludes outputs/ and logs/. Artifacts from a run are local only; a fresh clone has no outputs/demo_run until you run the demo. That is deliberate, but it means charts you are looking at may be stale relative to the code.

15Limitations, stated honestly

One scored date is not an experiment

Ten trading days, minus four consumed by the rolling window and one by the missing next-day label, leaves five feature dates. A four-date warm-up leaves exactly one forecast origin. Every metric on this page rests on six numbers produced on a single day. The correct reading is "the pipeline runs end to end", not "ridge beats persistence".

The data has no known origin

raw_manifest.json records no vendor, no extraction date, no method. The reference docs say the prices may be synthetic. Every downstream statistic inherits that uncertainty.

No uncertainty on any number

The metrics are point estimates with no confidence interval, no Diebold-Mariano test (the standard test for whether one forecast is genuinely better than another), and no bootstrap. At six observations none of those would be meaningful either, which is the deeper problem.

One number per day discards most of the data

The pipeline reads 23,400 minute bars and reduces them to 60 daily numbers, then to 30 modelling rows. Well-known refinements are absent: no jump-robust estimator such as bipower variation, no correction for the bid-ask bounce that inflates realized variance at high sampling frequencies, no overnight-return component, and no signature-plot check that one minute is even the right sampling interval for this data.

The model set is deliberately small

Three rules only. There is no HAR model — the heterogeneous autoregressive model, which regresses tomorrow's realized variance on its own daily, weekly and monthly averages and is the standard benchmark in this literature. There is no GARCH model and no hyperparameter search; ridge_alpha is fixed at 1.0 rather than chosen on a validation window. This is a scope decision stated in the README, not an oversight, but a reader should know what is missing.

Pooling six symbols into one regression

The ridge model fits one set of weights across all symbols at once, treating an AAPL row and an XOM row as interchangeable observations. That is a real modelling assumption — that the relationship between recent and future choppiness is the same for every stock — and it is nowhere stated or tested. It also means the residuals within a date are correlated, which any later attempt at inference would have to account for.

One thing the tests cannot tell you

They confirm the code does what it was designed to do. They cannot confirm the design answers the research question, because that needs more than one scored date. Passing tests and a meaningful result are separate claims, and only the first one holds here.
